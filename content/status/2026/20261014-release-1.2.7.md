{{% notice note "Update: use 1.2.8" %}}
The reuse of snapshot images in the matte renderer introduced a regression: animations with track mattes of different sizes could show horizontal streaks during playback ([issue #12](https://github.com/lottie4j/lottie4j/issues/12)). This is fixed in [Lottie4J 1.2.8](/releases/#2026-10-15-128), so please use that version instead of 1.2.7.
{{% /notice %}}

## 1.2.7 Stops Doing the Same Work Every Frame

[Lottie4J 1.2.7](https://github.com/lottie4j/lottie4j/releases/tag/v1.2.7) is a performance release. While profiling a JavaFX application with an animated logo, about 80% of the JavaFX thread's time went to one thing: decoding the same embedded PNG image over and over again, on every single frame.

Two fixes in the player:

* **Image assets are decoded once.** Each `LottiePlayer` now caches the decoded images per asset, and preloads them all when the animation is loaded, so the first frame doesn't stall. Assets that fail to load are cached too, so a broken image no longer logs a warning 60 times per second.
* **Cheaper track mattes.** The matte renderer now reuses its off-screen canvases, snapshot images and pixel buffers between frames, and skips the pixel sampling that was only needed for debug logging.

In the profiling run, GC pauses dropped from 531 to 177 in 22 seconds, PNG decoding disappeared from the hot methods, and allocations in the matte compositing went from 30% to almost nothing. Animations with embedded images or mattes should use noticeably less CPU and battery.

The file viewer also got fixes for leaked players and bindings when loading another file, and a non-blocking shutdown of the WebView comparison. A new profiling harness in [`tools/profiling`](https://github.com/lottie4j/lottie4j/tree/main/tools/profiling) makes it easy to repeat these leak and threading checks.

See the [full changelog](/releases/#2026-10-14-127) for the details, or the [GitHub diff](https://github.com/lottie4j/lottie4j/compare/v1.2.6...v1.2.7) between 1.2.6 and 1.2.7.
